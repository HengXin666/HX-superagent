## 任务

### 任务 1

# 目标
确认本轮改动没有带来任何新的测试失败: 改动后的全量测试结果与改动前的基线逐条对得上, 只多出新增用例且全部通过.
# 背景
工作区本身就有已知失败(服务脚本类用例依赖 tmux/进程环境, 飞书事件消费者有一个时序竞争), 不先跑基线就无法判断失败是不是本轮引入的. 基线必须来自改动前的同一份源码, 不能拿正在被改的副本去跑, 否则结果会被半成品污染. 相关目录: src/, tests/, docs/.
# 步骤提示
在改动前的快照上单独跑一遍全量测试拿到基线失败清单, 再在改动后的源码上跑一遍, 按"用例名"做集合对比. 语言环境统一成 C, 避开已知的本地化文案差异. 文档类检查(模块表/测试表)也算在内.
# 交付物
两份失败清单和对比结论(新增失败 / 消失的失败 / 新增用例), 写进本轮结果说明.
# 验收标准
LC_ALL=C pnpm vitest run 在改动前后各跑一次; 改动后的失败用例集合是基线失败集合的子集, 新增测试文件全部通过; LC_ALL=C pnpm typecheck 无输出退出码 0.
# 已知风险
服务脚本类用例耗时长且受机器环境影响, 两次结果可能有抖动; 遇到只在一侧出现的失败要单独重跑确认, 不能直接归为本轮引入.

### 任务 2

# 目标
把镜像里验证过的改动安全写回本地工作区, 不覆盖用户在这段时间里自己做的任何修改.
# 背景
真实工作区(feat/panel-v2 分支)有大量未提交改动, 而且用户可能同时在编辑; 本轮是在一份镜像副本上改的, 写回时只能动本轮真正改过的文件. hxoa 只有读写和只读 git, 没有删除和合并能力. 相关目录: src/client/, tests/, docs/.
# 步骤提示
以镜像建立时的文件内容为基准, 写回每个文件前先读一次工作区当前内容, 与基准逐字节比对: 一致才写, 不一致就跳过并记入冲突清单, 交给用户手动合并. 新文件写前确认不存在. 构建产物目录不写回, 让用户自己重建.
# 交付物
写回成功的文件列表、跳过/冲突的文件列表(如有), 以及每个文件写回后的版本号.
# 验收标准
每个写回文件在写回前与基准一致(比对结果 SAME); 写回后用只读 git 查询看到的改动只出现在本轮列出的文件上; 冲突清单为空, 或每个冲突都写明了原因.
# 已知风险
比对和写入之间仍有很短的竞争窗口; 用户若在开会期间改了同一文件会进冲突清单而不是被覆盖. 根目录下之前误建的 git 空文件 hxoa 删不掉, 需用户手动删除.

### 任务 3

# 目标
交给用户一份能直接审阅和复用的补丁, 加上所有实际改动过的文件绝对路径, 按四块需求归类.
# 背景
用户要的是"补丁 + 实际改动文件路径", 不要再一轮计划或确认. 补丁要只含本轮改动, 不能混进工作区里原有的未提交修改. 相关目录: src/client/, tests/, docs/.
# 步骤提示
从镜像的基准提交生成统一 diff(新增文件也要进补丁), 以绝对路径列出文件, 按"预设 / 交互与外观 / 架构图 / 监控台 / 测试与文档"归类, 并说明哪一块已在源码中具备、本轮只做了增量.
# 交付物

在改动前的快照上执行 git apply --check 补丁无报错; 清单里的路径与补丁里的文件一一对应, 不多不少.
# 已知风险
