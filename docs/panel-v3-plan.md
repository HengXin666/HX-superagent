1. **不再停在计划, 要落地.** 上一轮的问题是「写了很多, 但没提交、没上实例、你看不到」. 所以这次判断成功的唯一标准是: 工作区里有真实文件, 实例上有截图.

## 三、落地前提 (诚实说明当前卡点)

目前经 hxoa 映射只能读写文件, 有三件事做不到, 落地前必须解决:

- **不能执行命令**: 映射没有 exec, 所以 `pnpm check`、构建、测试都跑不了.
- **git 被拒**: 经映射执行 git 返回「/home/hx 不在读写挂载根之下」, 所以没法整理基线提交、开分支.
- **依赖装不了**: 仓库依赖 `@deepseek-ai/*` 0.2.1-alpha 系列, 公共 npm 上只有更旧的版本, 我这边的沙箱装不全, 也就没法替代本机做验证.

没有这三样, 写进仓库的代码无法类型检查、无法测试、无法截图, 等于重演上一轮的失败. 解决办法二选一:

- 在 hxoa 服务端为本仓库开放受限的命令执行 (pnpm, git status/diff/add/commit/branch, 启动测试实例);
- 或者由你在本机执行每条线验收段里的命令, 把输出贴回来, 我按结果迭代.

### 线2 统一预设: 自定义 + 多选叠加 + 效果预览

# 目标
面板里只有一个用户能理解的「预设」概念: 用户可以新建/复制/编辑/导入导出自己的预设, 为主 Session 和执行器各自勾选多个预设按顺序叠加, 并实时看到叠加后的最终效果 (可用工具、追加指令、提示词片段) 和冲突提示; 在真实运行的面板上能完成这一切.
# 背景
用户反馈运行时无法多选预设、只能用内置的. 现状是三套并存的概念: DSH Agent 预设 (单选卡片, 受 DSH 注册表限制无法运行时新增)、上一轮新增的「能力包」(可多选叠加)、Prompt 预设 (本就支持多选, 疑似运行实例构建过旧所以看不到). 用户心智里这是同一件事. 相关目录: src/app (预设与设置的后端)、src/client (面板)、src/policy 相关配置、docs (005/007 文档). 上一轮的交付说明在 docs 目录.
# 步骤提示
先用最新构建在真实 DSH 实例上复现用户的问题并截图, 确认是构建过旧、入口难找还是模型本身不对. 再设计统一的预设模型: 建议以「一个基础 Agent 预设 + 有序叠加的 N 个用户预设」为骨架, 用户预设可同时携带工具收窄/授予、长期指令、提示词片段, 把能力包和 Prompt 预设收拢为同一入口 (底层存储是否合并由你判断, 但界面上必须是一个概念). DSH 注册表做不到的部分 (例如新建 DSH 级 Agent 预设) 要明确边界并在界面上说清楚, 不要假装支持. 老配置必须无损迁移. 交互上参考用户的操作习惯: 勾选、拖拽排序、即时预览、冲突就地提示, 多面板同时打开时实时同步.
# 交付物
独立分支上的代码改动 (后端、面板、迁移、测试) 与更新后的文档; 一份简短报告放在 docs 目录, 包括诊断结论、最终模型、与上一轮能力包/Prompt 预设的取舍、DSH 限制说明、真实实例截图 (多选前后对比). 回报写清改了什么、没做什么、为何偏离提示.
# 验收标准
1) pnpm exec tsc --noEmit 退出码 0; env LC_ALL=C pnpm exec vitest run 全部通过, 且新增覆盖: 自定义预设增删改、多选顺序叠加、去重、冲突拒绝、老配置迁移; pnpm build 成功.
2) 在真实 DSH 实例上 (重新构建并重启后), 能新建一个自定义预设, 为执行器同时勾选至少 3 个预设并调整顺序, 预览区实时显示最终工具与指令, 保存后新建的 Session 实际按叠加结果运行 (以会话的工具列表或提示词为证), 附截图.
3) 界面上用户只需在一个地方完成以上操作, 不需要理解三套概念.
4) 另开一个面板窗口, 一边保存另一边无需刷新即更新.
# 已知风险
DSH 注册表不支持运行时注册新 Agent 预设, 真正的「自建 DSH 预设」可能需要改 bundle 的补丁配置并重启, 需与用户确认是否接受; 合并概念涉及存储迁移, 处理不当会丢团队已有配置; 执行器必须保留读/执行/写文件等底线工具, 叠加规则不能被用户预设绕过.

### 线3 设计系统落地与交互实时化

# 目标
整个面板换上统一、有质感的现代设计语言, 所有页面使用同一套组件; 数据层做到「所见即当前真实状态」: 改动即时反馈、他处变化自动刷新、详情不丢列表上下文, 交流程序符合用户意图和操作习惯.
# 背景
用户认为 UI 组件低级廉价、交互不实时且有不合理处. 上一轮已在 src/client 下产出组件库 v1, 并在 docs 目录留下交互审计清单 (按 P0/P1/P2 分级, 含实时数据现状与订阅建议) 和视觉方向文档, 但只迁移了部分页面, 审计中的 P0/P1 大多未落地. 面板代码在 src/client, 实时事件与接口在 src/app. 颜色只能用 DSH 的 alias token, 需要随 DSH 主题切换明暗.
# 步骤提示
先在真实实例上逐页走一遍真实使用路径 (处理一张需要人的工单、改一条设置、查一条消息的来龙去脉), 录屏或截图, 标出「廉价感」和「不实时」的具体位置, 用来校正审计清单的优先级. 建议先补共享查询缓存/订阅层 (去重请求、按实体过滤事件、断线兜底只对可见页、乐观更新与回滚), 再全面迁移页面到组件库, 最后打磨动效、空状态、骨架屏、确认策略、键盘可达性和统一的搜索/命令面板. 视觉方向文档可以修订, 但改动要说明理由. 配置地图与监控台两条线 会复用你的组件和数据层, 接口尽早稳定并写进组件库目录的说明.
# 交付物
独立分支上的代码改动与测试; 更新后的审计清单 (逐条标注已完成/放弃及理由); 真实实例上各主要页面改造前后对比截图, 放在 docs 目录下的报告里. 回报列出完成的审计项、遗留项和偏离提示之处.
# 验收标准
1) tsc、全量 vitest (LC_ALL=C)、pnpm build 全部通过, 新增覆盖共享数据层 (去重、事件过滤、乐观回滚) 与关键组件.
2) 审计清单所有 P0 完成, P1 完成不少于 80%, 其余写明理由.
3) src/client 下页面不再直接使用旧的零散控件样式 (可用 grep 旧类名统计, 剩余处须有理由); 颜色不出现硬编码值, 可用 grep 检查 #000/#fff/rgba( 的残留并逐条解释.
4) 真实实例上: 列表点开详情为抽屉且关闭后回到原位置; 暂停/重试/停止点击后立即有反馈; 另一窗口的改动无需刷新即出现; 明暗主题下均无对比度问题. 附截图.
# 已知风险
迁移面大, 容易与 其他功能线 同时改到同一批页面产生冲突, 需先约定合并顺序; 共享缓存改造可能引入状态错乱 (例如筛选切换闪旧数据), 回归测试要足; DSH 设计 token 的可用范围受宿主版本限制.

### 线4 配置地图: 架构/调用关系图与编辑定位

# 目标
在配置区域提供一张可交互的「配置地图」(架构图/调用关系图): 用户随时看得到整个调度链路的抽象结构, 知道自己正在编辑的是哪一步、哪个区块、哪一段甚至第几行, 点击图上任一节点能直接跳到对应配置, 并能看到某一项配置会影响哪些下游环节.
# 背景
用户反馈配置项分散, 编辑时不知道自己在改哪个步骤的哪段内容. 上一轮已把设置页顶部流程图升级为五步架构图并支持聚焦高亮与面包屑, 但未在真实实例验证, 且只覆盖设置页、表达力有限 (无调用关系、无影响范围). 链路概念见 docs 目录里的领域模型、执行、提示词和架构文档; 面板代码在 src/client.
# 步骤提示
先在真实实例上评估现有架构图是否真的让人「不迷路」, 找几个典型编辑场景 (改主 Session 提示词的某段、改执行器预设、改某个 Source 的准入) 检验. 建议图的数据完全来自真实配置与预设叠加结果, 而不是写死; 节点粒度可分层展开 (步骤 → 区块 → 字段/提示词段), 编辑焦点双向联动 (编辑时图上定位, 点图时编辑器定位); 可以考虑展示调用关系 (哪个 Session 调用哪些工具/技能、提示词由哪些片段按什么顺序拼成) 和影响范围. 是否引入图形库、用 SVG 还是其他方式由你判断, 但要与 设计系统线 的设计语言一致、在窄屏下可用, 并与 监控台线 监控台共用同一套链路节点定义, 让「配置的结构」和「运行时的流转」是同一张图的两种视角.
# 交付物
独立分支上的代码改动与测试; docs 目录下的报告, 含交互说明、节点模型说明、真实实例上至少 3 个编辑场景的定位截图. 回报说明与上一轮架构图的取舍.
# 验收标准
1) tsc、全量 vitest (LC_ALL=C)、pnpm build 通过; 新增测试覆盖: 节点由真实配置生成、聚焦字段时正确节点与路径被标记、点击节点跳转并聚焦正确字段.
2) 真实实例上, 在 Source、Eval、执行、提示词、预设各选一处编辑时, 图上都能准确定位到对应节点并显示到段落或行级的路径; 点图上节点能在一次点击内跳到对应字段. 附截图.
3) 修改配置并保存后, 图无需刷新即反映新结构 (例如新增一个预设或 Source 实例).
4) 找一位没参与开发的人按截图走一遍场景, 不借助说明即可说出「我在改哪一步的哪一段」(写进报告即可).
# 已知风险
节点过多会让图变成噪音, 需要分层与折叠策略; 与 统一预设线 的预设模型强相关, 预设结构变了图要跟着变, 应在 统一预设线 模型定稿后再收尾; 图形库体积可能影响面板加载.

### 线5 实时监控台: 调度流转、执行现场与介入

# 目标
提供一个实时监控台: 用户能一眼看清外部消息从哪来、在调度链路中流到哪一步、每个执行器槽位和主 Session 此刻在做什么 (工具、命令, 敏感信息脱敏)、哪些事卡在人身上, 能追溯任意一张工单的完整调用链与耗时, 并能就地介入 (打开会话、暂停、停止).
# 背景
用户希望看到外部调度的情况以及我们这边正在做的事. 上一轮已在后端增加流转阶段事件, 前端 Console 增加节点脉冲动效和工单调用链, 但从未在真实流量下验证, 实时性和信息密度是否满足用户未知. 实时事件机制与接口在 src/app, 面板在 src/client, 面板与架构的说明在 docs 目录.
# 步骤提示
先在真实实例上制造真实或模拟的流量 (几条 GitHub/飞书触发、一两张并发工单、一次失败重试), 观察现有 Console 能否回答: 现在系统在忙什么、哪里堵了、哪件事需要我、这张工单为什么慢. 以这些问题为纲重新组织监控台, 链路节点定义与 配置地图线 配置地图共用; 建议包含全局吞吐与积压、链路实时流转、执行槽位泳道、需要人的事项、事件流 (可暂停/筛选/导出) 与单工单调用链的下钻. 后端事件若有缺口可补, 但要控制事件量与敏感信息. 数据层复用 设计系统线 的共享订阅层, 断线时要有清晰的状态提示而不是静默过期.
# 交付物
独立分支上的代码改动与测试; docs 目录下的报告, 含真实流量下的监控台录屏或截图序列、新增或修改的事件说明、性能观察 (事件频率、前端渲染开销). 回报说明与上一轮 Console 的取舍.
# 验收标准
1) tsc、全量 vitest (LC_ALL=C)、pnpm build 通过; 新增测试覆盖阶段事件生成、事件按工单过滤、调用链时间排序与耗时计算、敏感信息脱敏.
2) 真实实例上触发至少 3 条消息和 2 张并发工单: 监控台在事件发生后 2 秒内反映到对应节点与槽位, 无需刷新; 点任一工单能看到从触发到结束的完整调用链与各步耗时; 能从监控台直接打开会话或停止工单. 附截图或录屏.
3) 断开实时连接时, 页面明确显示断线与数据时效, 恢复后自动续读不丢事件.
4) 页面长时间打开 (至少 30 分钟持续事件) 不出现明显卡顿或内存持续增长, 在报告里给出观察数据.
# 已知风险
高频活动事件可能拖慢前端或撑爆事件流, 需要节流与上限; 命令和参数里可能含密钥, 脱敏遗漏是安全事故; 真实流量依赖 GitHub/飞书接入, 不具备时需要可信的模拟流量方案并在报告中说明.
