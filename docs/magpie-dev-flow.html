yetone/magpie 的实际开发流

一个几乎全部由 agent 编写、评审、合并、发布的开源项目，从想法到用户手里要过哪几道闸门。基于完整 git 历史（HEAD 12610cf2f，2026-11-12 00:25 +0800）与仓库内 LESSONS.md、docs/code-standards.md、docs/contributors.md、.github/workflows/test.yml、release.yml 逐条阅读整理。

先分清两个 magpie。本文讲的是 yetone/magpie：MIT 许可的模型网关（让 Claude Code、Codex、Gemini CLI 等换用任意模型）。apache/magpie 是 ASF 董事会 2026-06-17 决议成立的顶级项目，前身是 Airflow PMC 下的 apache-steward，给开源维护者用的 agent 工作流框架，与 yetone 的项目毫无关系。

2 每道闸门：判据和执行者

闸门判据谁执行
G0 读报告读完整个帖子到最后一条（10-13 有人在报告者说“先别做”之后还做了，被 revert）；用报告者的服务商、套餐、agent、界面（GUI/TUI/CLI）复现；测试夹具用报告里的原始字节agent 会话
G1 查危害
（仅社区 PR）		五类风险命中即停审；三种情况直接关闭（见第 4 节）agent 查，维护者裁决
G2 写改动code-standards 的“改动包含什么”10 条和“测试”9 条；一个提交一个目标；在自己的 worktree 里干，提交后 git show --stat HEAD 只能有自己的文件agent 会话
G3 本地验收六条验收标准；跑了什么、输出什么写进 commit 正文；没跑的必须写“没跑”，不能省略写改动的 agent
G4 合并（PR）维护者拉取 head，合到当前 main 上重跑；在 PR 上写明跑了什么、在哪个 head，再用 gh pr merge --match-head-commit <sha>，评审期间有人推送就会挡住合并；Draft 不能合维护者（agent）
G5 CI推到 main 和每个 PR 都触发；ubuntu/macOS/Windows 三系统；Linux 上 gofmt；vet；go test -timeout 30m；gateway 的 race 分片；Windows 专项；Linux 和 Android arm64 的纯 CLI 构建；安装脚本和官网测试。main 上的运行不被下一次推送取消GitHub Actions
G6 打 tagtag 的提交（或包含它的更新提交）上有一次跑完的绿色 CI，被取消的不算，第二次重跑才绿要看第一次；tag 在 main 上；先 git fetch --tags 找下一个空闲版本号（10-12 两个会话一分钟内给同一个提交打了两个 tag）agent 会话
靠自觉，没有机器拦
G7 派发推 v* tag 触发；用 owner 的 PAT 向 magpie-releases 发 dispatch；遇到限流就等重置，最多 65 分钟（v0.1.3561 到 3573 曾因限流没发出去）GitHub Actions
G8 算不算发布magpie-releases 签名、公证；主仓每 30 秒查一次，最多等 330 分钟，等齐 16 个资产；复制回来，只有比已发布的都高才标 Latest；没有中文说明就在固定 issue 里报一声GitHub Actions + magpie-releases
要点① main 上的 CI 不会被下一次推送取消：test.yml 写的是 cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}，注释引用 LESSONS。原因：10-28 时 main 最近 58 次测试有 49 次被取消，发版等不到一个真正跑完的绿灯。PR 上的仍然会被取消。
要点② 绿灯是规矩，不是锁：release.yml 只认 tag，不查 Test 的结果。code-standards 要求“发布要满足四条”，LESSONS 也记了 11-10 三个提交“在 CI 跑之前就推送并打了 tag”，并写了“把规则写在这里没能传到那些会话”。这是整套流程最薄的一环。
要点③ tag 不等于发布：tag → release.yml 派发 → magpie-releases 构建签名公证 → 16 个资产齐 → 复制回主仓并判定 Latest。v0.1.1213、v0.1.1218 打了 tag 却从未发布，第一个 1.5 小时没人发现（#1846）。

3 LESSONS.md 怎么运作

每条教训的段落结构

  1. 一句加粗的规则
  2. 证据列表：具体提交 hash、issue 号、报告者，以及当时出了什么事
  3. 常有一条“做对了的样例”（Done right）
  4. 常有一条“下次怎么查”
  5. 结尾 - Seen N× (日期, 日期)

Seen 按天，不按次

10-05 “修复要覆盖所有同类”出现了六次，也只算一天。目前文件里 55 条带 Seen 的：43 条 1 次，11 条 2 次，1 条 3 次（规则已在 code-standards）。

升级条件

文件开头原话：在 3 个或更多不同的天被复盘发现，就移进 code-standards.md。移走后：

  • 规则和证据写进 code-standards 的表格或验收标准
  • LESSONS 的“Moved to the code standards”一节留一行，括号里是那几天的日期
  • 之后再犯，按日期追加“criteria still missed”，作为证据继续累积

“Moved to the code standards”一节列了什么

升级日规则
10-07修复覆盖所有同类；改动要重推依赖它的一切；main 上红的测试是现在就要修的 bug；只合评审过的 head，合并前写清跑了什么
10-08上线前真实使用；GUI 测试两种引擎、窄屏、每种语言
10-11测试启动的东西随测试结束；时间相关测试两头留余量
10-14读取或解析失败等于“未知”；持锁时不做可能阻塞的事；别的应用的值取自那个应用；以保证命名的测试在保证被破坏时必须失败；测试不碰网络；tag 要等绿灯，tag 不等于发布；大提交要有写明跑了什么的正文
10-18magpie 的默认值不覆盖用户自己设的值；checkout 和 worktree 属于创建它的会话
10-28一个提交一个目标；红测试的 issue 要读到最后一条，上面的补丁优先采用；mover 的 min 版本跟上 npm 当天的版本

再往下一层：规则变成机器检查

一次事故→LESSONS 教训→ 3 个不同的天 →code-standards 规则→CI 步骤 / guard 测试

test.yml 的注释直接引用了这些教训：gofmt 那一步写着“10-01 到 10-06 未格式化文件进了 main 8 次”；main 不取消运行写着“见 LESSONS.md”。

节奏

设计上叫“夜间复盘”，实际是滚动的：11-11 一天就有 16 次 LESSONS 提交。

4 社区 PR 的两道关

第一关：先查危害，再评审

命中任何一条就停审等维护者，并且在维护者放行前不能在有真实账号的机器上跑它的代码：

  1. 改了 .github/、发布或发版脚本、Dockerfile、site/
  2. 新增网络地址、上传、遥测，或把凭证、token、cookie、文件发到以前没去过的地方
  3. 读写目标不需要的凭证文件、钥匙串或 agent 配置
  4. 新增依赖、go.mod 的 replace、npm 安装脚本、二进制、压缩或编码过的块、运行时拼出来的代码
  5. 加了中转、转售、推广地址，或维护者已移除的厂商

直接关闭、不评审的三种

  • 推翻维护者已裁决的东西（比如逐字节保留的 Codex prompt 文件）
  • 因想法被关后原样重提，没有回应关闭理由的新东西
  • 几秒内连开的近乎相同的 PR

第二关：正常评审

按 code-standards 的“评审 PR”清单：亲手跑、故意把它弄坏看测试能不能抓到、去读厂商源码而不是信 PR 的描述、查各平台、走完整条路径。

名单含义

5 验收六条：哪些机器能校验

#内容判定说明
1有一个去掉改动就失败的测试半机器回退再跑可以脚本化，但“失败的是不是它声称的行为”、编译错误和跳过不算，得人判断（10-12、10-13 都有测试在旧代码上照样通过）
2测试在沙箱 HOME 里跑基本机器testenv 和 TestMain 的标记有 guard 测试，没设就红
3构建和全量测试完全机器gofmt、vet、build、test 都是命令，CI 也在跑。难点只在人会偷懒跑 -run 或挑包
4GUI 测试两种引擎、每种语言能跑没人强制Playwright 可以自动，但 CI 不跑这一套，只能本地跑；“这次要不要跑全套”是判断
5尽量真实使用主要靠人要真实账号、真实厂商回复、Windows 实机；做不到要明说
6UI 规则一半一半t() 和翻译有 i18n-keys 测试，点击不滚动有 click-scroll 测试；不用原生下拉、不用彩色左边框条只能靠评审

6 对“自驱 PM”的启发

magpie 的需求入口确实是被动的（issue、Discord、X 上的报告）。它真正“主动”的部分是对自己的工作质量：每天复盘、找出反复出现的错误、升级成规则。

如果要做自驱 PM，最值得照搬的是这套按“出现天数”升级的阈值设计，只是把对象从“代码错误”换成“外部信号”：

外部信号→信号日志 + Seen 天数→ 3 个不同的天 →提给你的提案→ 你点头 →改动
  • 按天计数，过滤一次性的热闹，留下持续出现的需求
  • 每条提案带证据（来源、日期），和 LESSONS 一样可追溯
  • 每轮只提 1 到 3 条，小而有用
