先说结论（读完全文你会同意或反驳的六句话）

① 它不是一个独立服务，而是插进一个 DSH profile 的 3 个 cordis 插件，代码跑在宿主 DSH 进程里。 ② 它把「要不要做」和「怎么做」拆成了两个不同的 Session、两个不同的模型角色：主 Session 只做路由，Executor Session 才动手。 ③ 主 Session 的「只调度」靠专用 preset 收窄工具 + 输出 schema 硬限制 + 原文由宿主直送执行器，再加 system prompt；它仍保留 bash/read，「不读代码」是提示词规则（docs/007:507），兜底的是它写不进派工内容。 ④ 用户原话不经过主 Session 转述：Trigger 原文被存库，Executor 拿的是原消息 + 来源引用，主 Session 最多加 30 个字的「路由备注」。 ⑤ 调度是 2 秒一次的空转 pass + 事件唤醒，模型只在有活的时候被调用，不需要常驻对话。 ⑥ 它是单仓库设计（README 原话 for one GitHub repository），多仓多会话不是它的目标场景，但隔离键的设计给了扩展路径。

00 · ORIENTATION一分钟速览

如果你只读一节，就读这一节。下面四张卡片分别回答：它是什么、它不是什么、它由哪些部件组成、一次完整的活儿是怎么流动的。

它是什么

一个「主动式编程 Agent」：监听 GitHub（可选飞书）→ 判断这个请求该不该接 → 该接就开工单 → 在一个独立 Session、独立目录里把活干完 → 回到原对话交付。

它同时是一套「怎么和 Agent 协作」的方法论：尽量少占用人的注意力，尽量多给价值（docs/000-philosophy.md:5）。

形态上是 DSH 的 bundle：一个 cordis.patch.yml 往 profile 里插三个插件，外加两个专用 agent preset。

它不是什么

不是独立后端服务：没有自己的 HTTP server，没有自己的进程，管理 API 挂在宿主的 webServer 上，且只允许 loopback（src/app/http.ts:231）。

不是多仓库平台：一个部署 = 一个仓库 + 一个 Agent 账号（docs/006-deployment.md:5-7）。

不是「一个 Agent 干所有事」：主 Session 与 Executor 是两个预设、两套工具、两个模型角色，权限模型完全不同。

不是生产级软件：README 自述「研究原型，可能仍有 bug」（README.md:3）。

01 · PHILOSOPHY设计哲学：一切用「注意力成本」来审判

这个项目最不像普通开源项目的部分，是它先写了一份哲学，再写代码。所有设计取舍——少概念、少设置、面板只显示需要人的东西——都是这条原则的下游。

Take as little human attention as possible, and give as much value as possible. docs/000-philosophy.md:5 · 项目核心原则

这句话被拆成了两条可执行的下游规则：对 Agent 的行为约束，和对系统设计的约束。

对 Agent：五条行为律
  1. 只在被请求、或被书面规则允许时行动请求必须直接点名 Agent，且来自被允许的人；没人要求的工作需要团队自己写的规则，且先以「只记录不执行」的模式起步。
  2. 只在人必须行动、或能用到结果时说话接单时说一句并说清要做什么；干活时闭嘴；结果就绪、需要决定、做不下去时才再说话。
  3. 一次只问一个具体问题而且要用结构化字段问，否则问题会淹在长报告里。
  4. 按影响停下来，而不是按辛苦停下来本地改动可以做到可评审的结果；需要产品决策的改动必须停下来提问。
  5. 诚实汇报草稿标成未完成，失败就说失败，绝不为了不问人而绕过限制。
对设计：四条结构律

少概念。只有领域概念和它们的具体实现（GitHub、飞书）。一个业务需求要么变成某个概念的属性，要么变成一段 Prompt；不新增概念（docs/000:19）。

少设置。一个值能适配几乎所有团队时就给默认值；团队用文字描述的行为写成 Prompt，不写成设置项（docs/000:20）。

面板只显示需要人的东西。先列等你的，健康状态不占地方（docs/000:21）。

文档必须按序读。每篇只依赖前面几篇，读者永远不需要提前知道还没介绍的概念（docs/000:22）。

这条原则如何变成代码里的硬约束

哲学不只是标语，它在代码里有一串一一对应的落点：

因为它解释了后面所有「看起来过度设计」的地方。比如为什么主 Session 连写文件都不许、为什么一次请求要被拆成 Eval 和 Execution 两次模型调用、为什么面板上健康状态几乎不占位置——都是同一个取舍：人的注意力是稀缺资源，系统宁可多花算力也不能多花人的注意力。

读原文：docs/000-philosophy.md:1-33

02 · DOMAIN领域模型：Trigger → Eval → Ticket

整套系统只有一条主干：来源产生触发，触发按线程归组，评估决定要不要接，接了就生成带授权的工单，工单派给执行器，结果再从原渠道写回去。所有代码、工具、面板都只用这一套词（docs/001-domain.md:1-5）。

概念一句话它守的规则
Source 来源事件流（GitHub、飞书）持有读位置，重启不重放；过滤掉自己机器人的消息
Trigger 触发一个不可变事件同一触发接两次只建一张工单（幂等单位）
Thread 线程按时间排列的触发同一时间最多一个 Eval；评估中到达的触发并入下一批
Eval 评估对一批触发做决定两层：确定性 gate + 模型 assessment；自身无状态
Mandate 授权接单时授予的范围与强度不可变；更宽的范围意味着新工单；只有人能收回
Ticket 工单被授权的工作单位只有 Eval 能创建；状态自己定义，不跟 DSH Session 走
Assignment 派工工单与一个执行器实例的绑定一张工单可有多次派工；只有最终报告能结束工单
Subscription 订阅工单 ↔ 线程的多对多订阅线程上的消息直接送达工单，不经 Eval，也不带新授权

被刻意拒绝的概念（docs/001-domain.md:45-60）：跨来源的人员映射、Eval 自己排延时任务、"一个线程只能一张工单"、"追加到工单"这种 Decision、按主题相似度路由。每一条都是为了让模型少做判断、让数据结构多扛责任。

03 · AUTHORIZATION授权：Gate 由代码决定，Assessment 才交给模型

谁能让 Agent 干活，是宿主代码强制的；消息、评论、引用的文档只是决策的输入，改不了权限（docs/002-authorization.md:5）。

两条路径

Eval 路径：新消息先过 Policy.gate()。名单内的人点名 Agent → explicit；名单外 / 未点名 → 查准入表；名单里的机器人 → 最多 inferred；其他机器人不准入。

Subscription 路径：已有工单的线程上，人的跟进直接归该工单的执行器判断，不经 Eval、不产生 Decision；超出范围的由执行器 handback 交回，再走新 Eval。

接单模式

off：只处理明确请求。observe（默认）：推断的候选照样研判，但正面结论只记成"可接单，仅观察"。auto：推断的候选命中规则就接。

明确请求在任何模式下都有效。推断接单必须逐条判断每条启用规则，且实施意图、目标依据、是否需要设计决策都确定，否则记 directionUnsettled（src/policy.ts assessmentOutcome）。

规则、接单模式、各来源的名单 / 准入表 / 机器人名单合起来哈希成 Policy 版本。版本一变：进行中的 Eval 作废重排，受影响的进行中工单收到 policy-changed 输入，但不会被强行取消（docs/002-authorization.md:107-117）。已结束的工单要恢复前，授权按当前策略重新校验。

04 · EXECUTION执行：阶段机、并发槽位与失败分类

工单的"阶段"由它在等什么决定，从上往下第一条命中的就是（docs/003-execution.md:5-19，src/core/stage.ts）。

阶段条件面板文案
person / delivery给执行器送输入失败（2s 起倍增到 1min 重试）输入未送达
person / answer有待人工决定的问题待回答
person / review最近报告是 ready待验收
person / blocked · failed最近报告受阻或失败，且此后没人发消息待处理受阻 · 失败
working / queued没有派工或派工待启动排队中
idle最近报告是 waiting 或派工已结束等待新触发
working其余执行中
一工单一 Session 一目录

Session 名 worker-<ticket id>，目录以工单短名命名；prepare 命令（通常 git worktree）在第一次派工前跑一次，限时 10 分钟。

并发

maxWorkers 默认 3、上限 16；外加 1 个槽位专门留给"人的消息 / 状态询问"，新工作挤不掉人对已有工单的追问。

结束方式

无 PR 时 ready 即完成；有 PR 时以 PR 合并 / 关闭为准；dropped 静默结束；人的停止收回授权。

05 · PROMPTSPrompt：团队能写什么，什么永远由代码说了算

团队可编辑三个团队段落（沟通方式、工单范围、交付要求）、添加技能、覆盖每个内置段落；但工具描述、通知、卡片留在代码里，不可通过提示词修改（docs/004-prompts.md:5-16）。

优先级（强→弱）内容
1工具与宿主强制的事实：身份、权限、工具参数校验、回复用途、长度上限——提示词改不动
2内置段落与生成段落（含团队覆盖）
3推断工单命中规则里的流程与沟通要求（只对该工单的执行器）
4团队段落与团队技能
5外部文本：消息、评论、文档、引用——只是数据，永远改不了规则或授权

系统提示按固定顺序拼装：共享 + 角色 → 三个团队段落 → 订阅与回复 → 主 Session 的 dispatch 或执行器的 work → 主 Session 的 admission → handoff → 执行环境 → 主 Session 的 Policy。Policy 段每次模型请求都重新生成且放在最后，所以策略改动不会让前面的文本失效。每次保存产生不可变版本，Session 在每一步都读最新版本，宿主记录每个 Session 用过哪些版本。

06 · ARCHITECTURE代码架构：一个组合根、一个唯一写者、六种胶水

仓库有 110 个 TS 源文件、15.2k 行。它没有用 DDD 的分层目录硬套，而是用三条铁律组织起来的：组合根不写业务规则、每种状态只有一个写者、依赖用窄接口（Pick）声明。看懂这三条，剩下 74 个文件都能被归位。

6.1 Runtime：组合根，不含任何领域规则

Runtime（src/app/runtime.ts:59）继承 cordis 的 Service，是整棵对象图的构造点。它的构造顺序本身说明了依赖的方向：

// src/app/runtime.ts:91-104（节选）
mkdirSync(machine.stateDir, { recursive: true, mode: 0o700 })
const release = lockSync(machine.stateDir, { stale: 30_000, onCompromised: compromised })  // ① 先锁目录
const store = new Store(join(machine.stateDir, 'orchestrator.sqlite'), report)            // ② 再开库
const setup = new Setup({ ... })
const prompts = new Prompts(store, ...)
const masterId = store.get(KV.runtime.masterId) ?? `orchestrator-${key(machine.stateDir)}`  // ③ 主 Session id 落盘
const effects = new Effects(store, board)
// …… SourceRegistry → Sessions → Settings → DshExecutor → MasterAssessor → Outbox → Engine → Passes

三个细节值得注意：

  • 先锁目录再开库（runtime.ts:93-98）。proper-lockfile 保证同一 stateDir 只能有一个进程，避免两个实例同时迁移或写同一份 SQLite。锁丢失（onCompromised）会直接 abort() 整个 runtime。
  • 主 Session 的 id 是持久化的（KV.runtime.masterId），默认由 stateDir 哈希派生。重启后仍能找到同一个主 Session，而不是新建一个。
  • 循环依赖用 getter 打破：Engine 需要 Executor/Assessor，Executor/Assessor 又要回调 Engine，所以 Runtime 传的是 get engine() { return runtime.engine } 而不是构造好的对象（runtime.ts:128-137）。

6.2 Engine：唯一写者，拆成五个单向下游的部件

所有领域写入必须经过 Engine（src/core/engine.ts）。它的方法全是同步的，每个命令在一个事务里改完自己的聚合；端口把外部工作排进事务，事务提交后才由适配器执行。

部件职责依赖
Intake把 Source 的 Trigger 存一次、记到它的 Thread 上、扇出给订阅的 Ticket，并在非「人直接发来的消息」时排 EvalTickets
EvalsEval 的批处理、截止时间、过期重排、unavailable 判定，以及最终决策 accept/stop/ignore/unavailableTickets
Tickets从 accept 创建工单与 Mandate、Subscription、第一个 Assignment；工单的暂停/恢复/重试/重启/停止/结束Replies
Assignments记录 Executor 上报的事实：派工开始、输入送达/读取、崩溃中断、报告与待人工问题Tickets, Replies
Replies经 Outbox 写 Channel：确认、回答、结果、待人工消息，各按允许它们的规则无

为什么拆成五个部件而不是一个大 Engine？因为每条规则的验证成本不一样：Intake 与 Tickets 是状态机分支，Evals 是批处理与超时，Assignments 只是事实登记，Replies 是唯一出站口。拆开后 src/core 内部只依赖 EnginePart 基类（src/core/part.ts）的共享读，彼此不 import。

6.3 依赖规则：三条写进文档、靠测试兜底的铁律

规则一
显式窄依赖。每个类接收的接口只声明它用到的方法（大多是 Pick）：ExecutorHost、SessionsHost、HttpHost…… Runtime 只通过这类接口传递自身（docs/007:257）。
规则二
谁能 import 谁。src/core 不 import 外部（除 Node 哈希）且不做 I/O；src/sources 不 import src/app；面板只 import 类型和少量纯值（docs/007:258）。
规则三
一种状态一个写者。Trigger/Thread/Decision/Ticket/Assignment 只由 Engine 写；Settings 只由 Settings 写；Effect 行只由 Effects 写；Outbox 回执只由 Outbox 写（docs/007:259-269）。

第三条尤其关键：它意味着没有任何地方能「顺手」改一个 Ticket 字段。Source 想改工单，只能调 SourceContext.tickets.bindThread / threadClosed；Executor 想改，只能通过 6 个 orchestrator_* 工具。这直接决定了问题一里「主 Session 不能自己干活」是结构性的，而不是纪律性的。

6.4 Effects：唯一的持久化副作用队列

命令在事务内 enqueue(kind, key, payload)，只有提交之后才开始执行。同一个 kind/key 只有一行：重复入队会替换 payload 并立即可执行，但不改变队列顺序（src/app/effects.ts）。

kind做什么并发重试
assessment把 Eval 的候选卡片送进主 Session 的当前回合，然后告诉 Engine「已送达」以启动截止计时4，暂停时为 02s 起翻倍至 60s
launch启动一个待办 Assignment：prepare 命令 → 建 Executor Session → 发派工消息空闲 worker 槽位，暂停时 0模型/网络瞬时失败 5s 起翻倍至 300s，3 次；其他失败直接判工单失败
delivery把工单等待中的 Input 按序递给正在跑的 Assignment42s 起翻倍至 60s
relay把 worker 报告/问题、或人的追问，插进主 Session 的回合1，保序2s 起翻倍至 60s
notice往主 Session 注入通知但不唤醒它1，保序2s 起翻倍至 60s
reply通过 Source 发一条 Channel 消息（同一工单同一对话的前序消息未失败 3 次前要排队）15s 起翻倍至 300s
一张表看懂「为什么它扛得住重启」

六种副作用全部先落库、再执行。进程被杀，重启时 Effects.start() 会把未完成的重新跑一遍；relay 和 notice 保序，一个失败会挡住同类的后续项——这是「宁可慢，不可乱序」的取舍。抛 Later 表示「现在做不了」（比如没有空闲槽位），不计入失败次数（docs/007:170）。

6.5 Store：一个 SQLite 文件，7 张表

<stateDir>/orchestrator.sqlite，只由 Store 打开。所有时间统一存成 ISO 字符串，所以可以直接按文本比较大小；active / open / subscribed 这类「生成列」由 JSON 计算出来并带索引，因此一次 pass 只扫当前活跃的工作。

08 · QUESTION ONE问题一：会话管理者凭什么只"管事"、不"干活"？

先给结论：主 Session（代码和提示词里叫 orchestrator）不是靠"拿掉所有工具"来保证不干活，而是靠五道闸叠加；其中最关键的一道是结构性的——实现所需的上下文根本不经过它转述，所以它想"代劳"也拿不到足够的东西，想"误传"也传不进执行器的主输入。

8.1 五道闸：哪些是硬约束，哪些是软约束

#闸具体机制强度证据
1工具面收窄主 Session 用专用 preset dsh-superagent-router：没有子代理、web、文件搜索、写文件、todo、提问、展示、计划模式、插件管理、定时任务。应用工具只有 14 个 orchestrator_*：读、路由、重试 / 状态询问 / 备注、重新评估、研判三件套、回复、退订、改配置。硬cordis.patch.yml（router preset 注释）· docs/007:492-507
2不许等待noWait 护栏拒绝 sleep、shell timeoutMs > 30s、job 等待 > 5s；前台命令 5 秒转后台。它没法"开个长任务自己盯着"。硬src/app/sessions.ts:69-81

必须诚实说明的一点

主 Session 仍然有 DSH 的 bash、read、read_image、job_* 和 skill。文档原话："Avoiding code reads is a prompt rule, not a tool restriction."（docs/007-architecture.md:507）。所以"不读代码"是软约束；真正兜底的是第 3、5 道：就算它读了代码、想好了方案，也写不进派工——它能写的只有 30 词的路由备注，而执行器的主输入是宿主拼出来的原文。

8.2 不给它干活的工具，它有没有足够上下文"描述事情"？

有，而且是刻意只够路由、不够实现的那一份：

它看得到的
  • 候选卡片：批内触发卡片、线程、该线程的工单（进行中的在前，已结束的也在）、delivered_to、文本里提到的 PR/Issue 对应的 referenced_tickets、执行器交回的 handed_back 理由。
  • 研判窗口（仅推断候选）：触发正文 ≤ 4000 字符；线程前 5 条 + 触发前后各 5 条，每条 ≤ 400 字符（紧邻两条 ≤ 1200）；最多 8 张相关工单；其余消息只给 50 字预览，按需 orchestrator_eval_read 展开。
  • 回报：worker_report（摘要 ≤ 600 字符）、worker_attention（带问题）、follow_up 通知。
它看不到 / 不该看的
  • DSH 的编码提示词和仓库 AGENTS.md——只有执行器读（docs/004:61）。
  • 执行器的详细 transcript——提示词："Never read detailed transcripts to invent a plan."
  • 代码、日志、链接文档——非研判场景下禁止追（软约束）。
  • 它的"描述"只体现在三处：title（标签）、acknowledgement（一句话公开确认）、note（30 词路由背景）。

8.3 它理解偏了怎么办？防"传话失真"的六个环节

  1. 不转述，只转发派工必须带原始 trigger_id，宿主独立附上原文引用，与备注无关（"The host always includes the original trigger reference independently of the note"）；执行器"derive requirements from the original source"。主 Session 写错标题，执行器照样读到原话。
  2. 决策空间极小它只能在四种离散动作里选，没有"改写需求"这个动作。最危险的是 attach 错——会把整条线程订阅给错误工单——所以 attach 只允许在消息明确指向某工单（引用其 PR / Issue / 原消息 / 确认语，或"刚才那个改动"且恰好只有一个匹配）时使用，主题相似一律当新请求。
  3. 执行器先公开确认一次开工前在原消息下回复一句"对象 + 预期结果"（docs/004:83）。理解偏差在这一步暴露给请求人，人在原地一句话就能纠正，纠正消息经订阅直达执行器。
  4. 执行器可以退回不属于本工单的跟进 orchestrator_trigger_handback 交回，附理由，作为带 handed_back 的新候选回到主 Session；被错误关联的线程用 orchestrator_thread_unrelated 退订。主 Session 不能把交回的消息再关联回原工单（代码拒绝）。
  5. 问题原样转达执行器的问题放在结构化 human_action 里，主 Session 发 attention 时必须"copy the stored question into human_action"，不能翻译成自己的技术决定。
  6. 授权不靠理解谁能发起、强度多少由 gate 算；接单范围写进不可变 Mandate；推断接单默认只观察（observe），先看它"本会接什么"再放开。

残余风险（如实说）：title 和 acknowledgement 由主 Session 生成，可能措辞失准——但 acknowledgement 是公开贴在原消息下面的，偏差不会静默传播；批量路由时把 A 卡的 trigger_id 配到 B 卡内容上目前没有强校验，只能事后从 disposition 追溯（见 11.2 风险二）。

8.4 几十个仓库 × 每仓几十个会话，怎么保证不乱？

先纠正前提

一个部署只对应一个仓库：GitHub Source 只有一个 repository 字段，部署检查验证 Agent 账号对它有推送权限（src/deployment.ts:86-105）；状态目录加锁，一个目录只能一个进程。所以"几十个仓库"= 几十个 DSH profile（各自 stateDir、端口、主 Session、SQLite），它们之间物理上互不可见，不存在跨仓串台的通道。

单个仓库内几十个并行会话不乱，靠的是"状态在数据库里，不在模型上下文里"：

可能乱的地方防线
会话串活1 工单 ↔ 1 Session（worker-<id>）↔ 1 目录 ↔ 1 分支（agent/<短名>）；PR 按分支最后一段与工单短名匹配绑定
消息送错会话路由靠 Subscription（数据），不靠模型记忆；执行器只能读自己工单的资源，看不到其他工单与 Decision 的 id（docs/007:573）
重复接单触发入库去重；accept 按 trigger_id 幂等；同线程同时只有一个 Eval
并发写坏状态每类状态唯一写者（Engine / Settings / Prompts / Effects / Outbox），SQLite 单文件 + 目录锁；外部副作用先入 effect 表、事务提交后才执行
回复乱序同一工单发往同一对话的消息按入队顺序发出，确认一定先于结果
主 Session 上下文爆掉它不保存工作状态；压缩后按提示词"Check ticket summaries after compaction"从库里重读；一次 route 可同时决定 20 个候选；运行中到达的多条转达合并到下一步一次投递
资源被新活挤占maxWorkers 槽位 + 1 个留给人；超出的工单排队，面板 Overview 只显示待人处理的工单与真实问题

真要扩到几十仓库：零改代码的做法是"每仓一个 profile"，配一个外层脚本批量跑 scripts/dsh-superagent --profile <p> status 并汇总；要做成"一个实例管多仓"则需要 11.3 列的改造（Source 多实例、卡片加仓库维度、存储层重做）。

09 · QUESTION TWO问题二：内部模型是怎么被持续调度的？

没有常驻的"大循环 Agent"。持续运转靠三层：来源轮询把世界变化写成触发；每 2 秒一次的 pass 推进确定性状态机；持久化的 Effects 队列负责把工作"注入"模型会话。模型只在有活时被唤醒，干完就结束回合。

9.1 三个时钟

来源时钟

GitHub：轮询 notifications，间隔取 max(pollSeconds 默认 60, GitHub 要求的间隔)（src/sources/github.ts:128-144）；同时轮询进行中工单的 PR 与 CI、已订阅线程。订阅线程在工单存活期间及结束后两周内持续轮询。飞书：事件消费者实时收，外加历史补收与话题轮询。

Pass 时钟

setInterval(…, 2000) + 命令触发（src/app/passes.ts:28）。一次只跑一个 pass：先跑到期的 effects，再 Engine.evaluateDue()——给有排队触发的线程启动 Eval（每线程一个，期间到达的并成一批）、处理超时、恢复暂停期间被唤醒的工单。

模型回合

主 Session 与执行器都是"被喂一条消息 → 跑一个回合 → 结束"。新消息通过 DSH inbox steer 进正在跑的回合，下一步就能看到；没有回合在跑时则唤醒一个新回合。

9.4 出错与重启时它怎么续上

  • 瞬时故障（HTTP 408/429/5xx、连接被拒/重置/超时）：launch 重跑、回合失败的执行器在 15/30/60 秒后收到"继续"消息，共 3 次。
  • 受阻 / 失败：工单不再接收自动输入，工具仍可用，人可以直接进 Session 接手；人发消息、面板重试或后续非失败报告解除。
  • 进程重启：运行中的派工记"host restarted"，新派工带恢复说明（先查目录、git 历史和 GitHub，再决定是否重复外部动作），按最老工单优先恢复；会话、目录、订阅、待送消息全部保留。
  • 进程挂了：建议在操作员日常用的另一个 DSH profile 里建每小时检查，跑 scripts/dsh-superagent status，退出码 1 才 --respect-stop restart（docs/006:133-141）。
  • 暂停处理：停止派工、新 Eval、Eval 超时、送达和回复；来源继续记录触发，正在跑的回合不打断；Eval 截止时间顺延暂停时长。

原生不支持。在本地 DSH 再装一份本插件，会在本地起一个完整实例（要 stateDir、会去轮询 GitHub、会开自己的主 Session），不是瘦客户端；它的面板也只会连本机的 /orchestrator/api。

今天就能用的做法：把 DSH + 本 bundle 整个部署在服务器上，本地 ssh -L 3082:127.0.0.1:3082 server，浏览器打开 http://127.0.0.1:3082，在侧栏点 Superagent。Host 头仍是 127.0.0.1:3082，满足同源校验。

如果一定要"瘦入口"形态，需要改哪里

以下是改造方向，不是项目现有实现：

  • 客户端 src/client/api.ts 的请求基址可配置为远端；
  • 服务端 http.ts 的 loopback / 同源校验换成带鉴权的远程访问（token 或反向代理鉴权）；
  • “打开 Session”跨实例：本地 DSH 打不开远端 Session，需要远端会话的查看入口；
  • 本地插件只注册客户端部分，不加载服务端三插件。

第 07 节（面板复刻）就是这个浏览器端插件的 1:1 还原：真实面板挂在 DSH Web 的 main 槽位，入口是侧栏的锤子图标。

11.2 三个真实的工程风险

风险一 · 成本

每个请求至少两次模型调用（Eval 一次、Executor 一次），Executor 还可能跑很多轮。一次 proactive 观察即使最后 ignore，也已经花掉一次 Eval。

缓解：Eval 与 Executor 可以配不同模型（src/app/role-models.ts）；observe 模式只在 auto 之外记录不执行；规则不匹配时可以直接从卡片 ignore，不走完整 Eval（prompts/admission.md:1-4）。

风险二 · 串号

主 Session 是单点：所有候选卡片都进同一个 Session，靠卡片里的 trigger_id 区分。

缓解：工具调用强制带 trigger_id；Engine 幂等（同一 Trigger 接两次只建一张工单）；卡片是结构化字段而不是自由文本（src/app/cards.ts）。

残余风险：模型把 A 卡的 trigger_id 配到 B 卡的内容上——目前靠 Prompt 纪律 + 事后可从 disposition 追责，没有强校验。

风险三 · 排队

worker 槽位满时 launch 抛 Later，工单就排队；人发起的新工作不受影响（可以多用 1 个槽位），但 proactive 的会积压。

缓解：面板上 load 显示 running / queued / maxWorkers；pass 每 2 秒重试；暂停（paused）会冻结所有 launch 与 delivery 而不丢队列。

11.3 从「一个仓库」到「几十个仓库」：需要补什么

这是你问题一里最尖锐的部分。诚实结论：当前代码不支持多仓库，但它的隔离键设计没堵死这条路。按改造难度排序：

#要改的地方现状改造成本
1部署模型一个 profile = 一个仓库；deployment.repository 是单值低：按仓库跑多个 profile（不同端口 + 不同 stateDir），完全不用改代码
2Source 实例SourceRegistry 已支持多个 kind 与多个 instance，但 GitHub kind 的 config 只认一个 repository中：把 GitHub Source 改成「每个仓库一个 instance」，轮询各自游标
3主 Session单个 masterId，所有仓库的候选都进同一个 Session中：卡片已带 source 字段，可在卡片上增加仓库维度，并在 Prompt 里加「先按仓库分组再决策」
4执行环境executor.directory 与 prepare 命令针对一个克隆低：prepare 命令本身已经用变量模板（docs/006:186-192），按仓库参数化即可
5凭证一个 Agent 账号 + 一套 CLI 包装器中：每个仓库一个 Agent 账号，或一个账号加多仓库权限；worker-bin 的 shim 机制要按仓库切换
6数据规模SQLite + 无删除高：几十仓 × 几十会话的 Trigger/Decision 体量会先撑爆单文件库
一句话结论

「几十个仓库 × 每仓几十个会话」在当前原型里不是「配一下就行」，而是「6 处改造 + 一次存储层重做」。但如果只是「每个仓库一个实例」，今天就能用：dsh superagent --from-default-profile web 换个 profile 名、改端口与 stateDir 即可，代码零改动。

11.4 什么时候不该用它

  • 人很少、请求很少：两个 Session、两次模型调用的开销，抵不过一次手动 git commit。
  • 需要强隔离或合规审计：它跑在操作员的 OS 账号下，full-access；没有沙箱边界。
  • 要求确定性行为：Eval 是模型判断，同一段话可能今天 accept 明天 ignore（Policy 版本会变，模型也会变）。
  • 多仓库强需求：见 11.3。
